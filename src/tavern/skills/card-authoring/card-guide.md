# 角色卡创作与字段

角色卡把可持续互动的设定交给游玩模型。人物需要动机、边界和说话方式；世界或情境卡需要可行动的入口、关系和规则。避免用一串形容词替代具体行为，也不要替用户预先完成剧情。

## 字段分工

description 放不可缺少的核心设定，personality 补性格，scenario 说明当前互动背景。first_mes 是用户实际看到的起点，alternate_greetings 为独立可选开场。mes_example 展示语气与互动方式，不是过去已经发生的剧情。system_prompt/post_history_instructions 放确有必要的创作要求，避免互相矛盾或复制整个描述。creator_notes 是给读者的说明，不是模型必然收到的资料。

两种 Agent 模式均注入上述六类非空文本字段，分别包裹在 card_system_prompt、card_description、card_personality、card_scenario、card_mes_example、card_post_history_instructions 标签内。前五类放在固定资料区，后置要求放在当前输入之后；Half Agent 可按已保存配方调整。运行时只用标签标识字段来源，不另加用途说明或按字段名限制文本含义。只发送用户选中的开场，其余备选开场不作为剧情。卡内创作要求不替换运行规则或工具权限，运行必需信息不要只写入 creator_notes 或未知 extensions。

## 从零创作

**收集与方案**。先弄清题材与基调、卡的类型（单个人物、多人群像、世界/情境）、用户扮演谁及与角色的关系、期望的互动方式（日常、冒险、悬疑、经营等）和尺度边界。用户已经说明的不再追问；缺口只问会改变方案的几项。方案写明定位与核心冲突、用户角色、风格、开场方向与数量、世界书规划和必要机制，篇幅简短，便于用户逐项确认或修改。基于原著或真实资料时说明来源，改编处与用户确认。

**人物卡**。description 写清身份、外貌中有辨识度的部分、当前处境、想要什么与害怕什么、对 {{user}} 的初始态度及其原因。personality 用可观察的行为和反应写性格：面对压力、被冒犯、被关心时分别怎么做，口癖和说话节奏，不会做的事。给人物留出内在矛盾或秘密，让互动能推进关系，而不是只有固定反应。

**世界与情境卡**。description 写世界的基本规则、当前局势和用户能介入的入口；主要人物、地点、势力、物品和历史按需放进世界书。{{char}} 在世界卡中通常是叙述者或世界本身，在方案中说明清楚，开场和示例保持同一视角。

**开场**。first_mes 交代时间地点与氛围，让角色先行动或开口，并在结尾留下用户可以回应的空间；不替 {{user}} 说话、行动或决定感受。多个开场应提供不同的切入点（关系阶段、地点、事件），每个都能独立成立，不互相引用。篇幅与预期的回复长度相当。

**示例对话**。mes_example 用 `<START>` 分隔若干段，以 `{{user}}:` 和 `{{char}}:` 标注说话人，展示语气、叙述风格和回应长度。示例展示的是“怎么说”，不要写成已发生的剧情或重复开场内容。

**世界书**。每个条目只讲一件事（一个人物、地点、势力、规则或事件），正文自足，不依赖其他条目才能读懂。comment 写条目标题；keys 写正文中会自然出现的名称、别称和关键词，避免“他”“城市”等过于宽泛的词；必须同时满足的限定词放 secondary_keys 并设 selective。只有所有对话都必须知道的少量核心规则设为 constant。新增条目形如 `{"keys": [...], "content": "...", "comment": "标题", "enabled": true, "constant": false}`，通过 `patch_draft` 追加到 `/data/character_book/entries/-`，省略内部 ID；变量规则和初值按 runtime-guide.md 设置用途。

**宏与一致性**。用 `{{char}}`、`{{user}}` 指代角色和用户，不写死用户名字；各字段的人称、时态和设定保持一致，同一信息只在一处完整写出。默认制作完整文本卡，不为填满字段重复内容；变量、正则和脚本仅在用户需要时加入。

**制作步骤**。确认方案后，`create_draft` 的 `fields` 一次写入主要正文；世界书条目较多时分批追加；随后 `validate_draft`，按完整性提示补齐。用户提供头像图片并明确用途时用 `set_portrait`。最终回复概括卡片结构、开场与世界书条目，说明尚待用户决定或验收的部分，提醒审阅后保存。

## 修改与工具

新卡先说明人物/世界定位、用户角色、互动方式、风格、开场方向及必要机制，取得确认后再制作。可直接使用用户已完整给定的方案，不必重复确认已经授权的工作。创建时用 H 引用保存方案和确认原文；讨论尚未确认的内容不要升级为定案。

路径相对于原始卡片根，有 spec 的卡用 /data/...，旧卡用 /...。完整读取后再改，JSON Patch 的 add 要求父节点存在，数组追加用 /-。保留未知扩展、脚本、字面宏、作者资料和资源。现有 C 引用编辑后仍是同一卡的最新草稿。数组与对象两种 entries 均需保留原形。

世界书正文、标题、人物介绍等单个已有文本字段优先使用 set_text_field，提供 card_ref、path、完整 text 和 comment；由程序包装补丁，不手工构造数组或嵌套 JSON。开场使用 set_opening，结构修改或跨字段原子修改使用 patch_draft。当前上下文中版本仍有效的完整读取可跨轮复用；换窗、上下文重建或版本失效后重新读取 current，概览与搜索摘要不能代替完整读取。

普通文本卡不用增加 MVU、脚本或工作流元数据。需要 MVU 或脚本时读取共用 runtime-guide.md；MVU 设计无需先选择模式，只有特殊脚本能力影响方案时才确认兼容性目标。validate_draft 的完整性提示是创作检查，结构合法不能证明脚本可用。test_draft 只检查明确列出的本地行为；未覆盖的叙事质量由用户验收。

## 用户角色

用户角色库与角色卡分开，只含名称和介绍。只有用户本轮明确要求相关操作时才使用 list_personas、read_persona、create_persona、update_persona，并引用本轮最新用户请求 H 编号。普通制卡、{{user}} 宏、方案里的玩家定位和助手建议都不授权访问或配套创建用户角色。只查看不写入；修改前完整读取，以 P 编号定位并保留未要求修改的字段。用户角色在本任务正常完成后直接保存，停止或失败可续接，已有故事的身份快照不随之改变。
