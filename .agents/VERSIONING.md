# 版本号基准

本文件规定应用版本号如何判定与维护。只在用户明确提及版本号、发版或打标签时使用；日常开发不自行提升版本号，也不因提交数量或日期自动打标签。

## 当前阶段

- 应用版本采用 `MAJOR.MINOR.PATCH`，当前处于 `0.y.z` 实验阶段。Windows 与 Linux 共用同一版本号和标签。
- 版本号标识源码里程碑，不表示完成百分比，也不表示已发行安装包或通过发行验收。
- 已公开的标签保持固定，不移动、不重打。`v0.1.0`～`v0.4.0` 为补标，历史说明见 [版本记录](../docs/changelog.md)。

## 判定级别

自上一个标签以来的全部改动，取其中**最高**的级别。判定依据是用户从上一版升级时**是否需要额外注意**；项目没有二进制包，用户靠拉取源码升级，因此数据与行为兼容比代码改动量更重要。

**MINOR（`0.y.0`）**：满足任一条即可。

- 数据库 schema、设置文档版本或其他持久格式版本变化，需要迁移或备份。
- 提示词、上下文编排、工具协议或 MVU 处理变化，会改变模型输出或请求前缀缓存。
- 依赖、锁文件或前端资源变化，需要重新运行安装脚本。
- 新增用户可见的能力、设置项或界面入口，或移除、改变已有行为。
- changelog 需要写“升级注意”。

**PATCH（`0.y.z`）**：以上都不满足。修复与小幅界面完善，拉取后重启即可，回退时无需恢复备份。

**不需要发版**：纯文档、注释、测试、开发工具与 agent 指引的改动，在下一次发版时一并带上。

## 发版时机

- 按主题收拢后再发版，不按日期发。上一个标签之后仍在密集修改同一主题时，应向用户建议等待收拢。
- 打标签前构建和相关检查已通过；发行前的完整验证按 [AGENTS.md](../AGENTS.md) 的测试执行纪律，征得用户同意后执行。
- 级别有争议时，向用户说明触发 MINOR 的具体改动，由用户决定，不擅自降级。

## `1.0.0` 条件

核心行为与升级兼容约定已经稳定；最近一个完整 MINOR 周期内没有破坏兼容的数据迁移和协议改动；完成 [发行验证](../docs/development/validation.md)。满足后进入 `1.0.0`，此后 MAJOR 表示不兼容变更。

## 独立格式版本

应用版本与下列格式版本相互独立，各自只在对应格式变化时递增：

- 数据库 `meta.schema_version`（`src/tavern/storage/store.py`）。
- 设置文档 `version`（`src/tavern/core/settings.py`）。
- 剧情快照 `memory_document.version` 及上下文账本等模块内的 `VERSION`。

规则：

- 任何数据库结构变化（新表、新列、改变已有列语义）都必须递增 schema，不得在同一 schema 内靠检测列是否存在悄悄扩展。旧格式先只读核对、再备份、最后迁移并写入新 schema；旧程序遇到新 schema 时在写入前拒绝。
- 格式版本递增至少对应一次 MINOR 应用版本。应用版本提升并不要求格式版本跟着变。
- 格式版本变化时同步更新 [设置存储](../docs/reference/settings-api.md#数据库与设置迁移)、[安装与维护](../docs/guides/maintenance.md) 等写明当前版本的文档。

## 提升版本的操作

用户确认新版本号后，在同一个提交中修改以下全部位置，并用 `rg` 搜索旧版本号，确认没有遗漏：

- `package.json`、`package-lock.json`（根项目两处）、`pyproject.toml`、`uv.lock` 中的本项目条目。
- `src/tavern/application/api.py` 中的 `VERSION` 常量（FastAPI 与健康检查共用）。
- `README.md` 的版本徽标与正文、`docs/README.md`、`docs/guides/maintenance.md`。
- `docs/changelog.md`：更新“当前版本”和标签表，新增版本小节，写主要变化；有迁移、依赖或行为变化时写“升级注意”。

提交消息用“杂项：发布 vX.Y.Z”。标签使用带注释标签 `vX.Y.Z`，说明写成“vX.Y.Z：主题”。打标签前确认 `main` 与 `linux` 的同步状态，按用户指示处理。只有用户说“推送”时才推送分支和标签。
