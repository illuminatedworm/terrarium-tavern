# 本地运行时缓存断点控制

本地运行时控制的目的，是让长对话中的稳定前缀真正得到复用，避免默认缓存不断写入变化的上下文，反而增加费用。保持消息前缀稳定是必要基础，但不足以保证服务商能找到、读取此前的缓存；应用还需要控制缓存终点、保持协议转换后的边界，并在分支、编辑、换窗和失败时维护一致性。这是实现会话级断点规划和多协议适配的原因。

正文模型默认使用本地运行时控制，后台维护与角色编辑默认使用云端策略。模型高级设置可切换“云端默认 / 本地运行时控制”。云端模式不注入本地断点、附加缓存 JSON 或 Gemini 对象引用，仍允许服务商自动缓存；OpenAI 的独立时效参数仍按模型发送，Claude 原生在用户保存时效后发送顶层自动缓存控制。已经有可靠自动缓存的服务可以使用这个模式。

## 调查依据与适用范围

**调查日期及截止日期：2026-09-29。** 以下服务商机制与价格示例均为截至该日期的调查结果，用于解释设计取舍；后续接入和调优需要重新验证实际行为与计费。

调查发现，官方 API 与中转服务的缓存管理成本差异很大：有的服务会自动发现可复用公共前缀，有的依赖已有缓存端点、有限回溯和稳定路由；中转还可能在协议转换时丢掉缓存字段，或因更换上游而失去缓存。具体中转异常只代表当时的案例，不能推广为所有同类服务的行为。

截至调查截止日期，与设计直接相关的机制差异包括：

- OpenAI 的缓存查找受消息与内容块边界影响。扩展同一消息可能使旧缓存终点落在消息内部，无法继续作为可查找边界；受支持模型可用显式断点控制写入范围。
- Anthropic 的缓存查找依赖此前实际写入的端点，每个断点最多回看 20 个位置；把断点放在每次变化的内容之后可能一直写入而无法读取。位置按协议内容块计算，不能直接换算成 20 轮对话。
- DeepSeek 会发现公共前缀并建立独立缓存单元，Gemini 提供默认隐式缓存。云端可以承担更多管理工作，但隐式命中仍不是无条件保证。

这些机制差异是实现本地控制的依据，不意味着所有模型、兼容接口或中转都接受同一套参数。具体路径仍需检查最终请求、实际 usage 和计费。

## 为什么稳定消息仍需要稳定断点

设两次请求从 `A + B` 增长为 `A + B + C`，其中 `A + B` 完全不变。理想行为是读取旧缓存，只处理新增 `C`。但如果当前查找只认新的消息或内容块终点，旧终点已经消失，或者中转没有保留断点，服务商可能重新写入整个 `A + B + C`。逐字节相同的文本前缀因此仍可能无法复用已有缓存。

这个问题在本项目尤其明显：规则、角色资料、常驻世界书和工具定义很长，而 checkpoint、记忆、变量、预算提醒、本轮检索与要求会变化。若变化内容进入缓存前缀，历史越长，重复写入的代价越大。只优化上下文顺序，无法同时解决端点查找、协议语义与对象生命周期的问题。

本地控制分别处理三件事：

1. **稳定编译前缀。** 规则、对话偏好、常驻世界书与角色资料放在前部；历史及锚定世界书保持顺序。本轮世界书紧邻当前输入，动态内容放在后部。Half Agent 的作者注、记忆、状态后置；Full Agent 的 checkpoint、窗口状态、预算提醒后置。工具定义尽量稳定，不把每轮变化的提示塞进工具说明。
2. **选择并保持一个明确终点。** Full/Half Agent 共用当前分支的断点解析器。间隔内沿用同一条已完成 AI 正文回复的末尾，后续正文、当前输入和动态上下文作为后缀继续发送。保持断点不会停止历史增长，也不会裁剪后缀。
3. **按协议兑现边界。** 编译器保存与服务商无关的断点意图，传输层转换为内容块标记或 Gemini 缓存对象引用；预览、实际请求与工作记录使用同一计划。服务商拒绝控制时明确降级。

本地仍不能控制中转内部的上游账户、路由或缓存驱逐。实现复杂度用于维护应用能控制的边界与可观察证据；“参数已发送”不等于“缓存已命中”。

实现依次补齐了这些层次：`b7d2168` 统一双模式编译顺序、后置动态上下文；`c8ff24d` 统一四种协议的缓存控制与生命周期；`ff3cc5f` 增加会话跟进策略、手动定位与历史导航。当前默认跟进间隔为 5 轮。

## 默认 5/3：保守省钱策略

默认参数是 **每新增 5 轮已完成正文推进一次，每次定位到倒数第 3 个已完成 AI 正文回复末尾**。跟进间隔与目标位置是两个独立参数；只有推进时才重新取倒数位置，间隔内保持同一消息作为锚点。

**5 轮不是数学最优解。** 它是缺少可靠上游机制、实际价格和未来会话长度信息时的保守选择：让一个稳定前缀有多次被读取的机会，降低每轮移动都触发全前缀重写的风险，同时避免永久固定导致未缓存历史无限增长。代价是更多近期历史按普通输入处理。已证实支持可靠增量复用的服务可以缩短间隔；需要重建大缓存对象的服务可能适合更长间隔。

**倒数第 3 个来自编辑习惯。** 用户最可能修改最近两轮消息，因此推进时把这两轮留在断点之后，降低修改、重生成近期正文对已缓存前缀的影响。这是产品上的保守假设，不是 token 成本模型推导出的最优位置。它不禁止修改更早历史；若用户修改了断点之前的内容、角色资料、常驻设定或工具定义，缓存仍可能失效。间隔内锚点会逐渐变旧，不会始终维持精确两轮距离。

这套策略至少提供了可解释的省钱路径：假设某稳定前缀在 5 次请求中只写一次，其余 4 次都读取，写入单价为普通输入的 1.25 倍、读取为 0.1 倍，则这部分 token 的费用为 `1.25 + 4 × 0.1 = 1.65`，低于不缓存的 `5`，约节省 67%；若每次都全量重写，则是 `5 × 1.25 = 6.25`，反而更贵。这是截至 2026-09-29 的调查所述倍率下的示例，只计算复用前缀；整次请求还包括普通后缀、输出以及可能的对象创建和存储费。真实节省依赖命中、TTL 和实际计费，5/3 不构成任意服务商上的省钱保证。

## 成本模型与后续优化

先用简化成本模型分析跟进间隔与目标位置，再结合运行时的工具续答、编辑、换窗与缓存生命周期修正。模型可作为后续优化的基础，当前实现仍采用固定策略。下面使用 `M` 表示跟进间隔、`K` 表示倒数位置；默认即 `M=5, K=3`。

计算示例统一采用 **`S=6,000 tokens`、`q=1,500 tokens/轮`**，作为当前会话规模的取整估算。`S` 包含固定资料、规则与工具定义；`q` 包含每轮用户输入、AI 正文及随历史保留的动态世界书增长。二者使用同一本地参考分词口径，不代表服务商精确计费值。

设每轮平均向可复用历史增加 `q` 个 token。若每轮只有一次请求、历史只追加、缓存不过期、无编辑和换窗，则平均额外未缓存历史为：

\[
\bar U \approx q\left(\frac{M-1}{2}+K-1\right).
\]

这不含每次请求都必须处理的当前输入与动态后缀。代入默认 5/3，得到 `1,500 × (2 + 2) = 6,000 tokens`，即平均 4 轮额外未缓存历史。其中，5 轮间隔带来平均 `3,000 tokens` 的等待增长，倒数第 3 个目标再保留 `3,000 tokens` 的近期历史。

### 增量复用成立时

若推进断点能读取旧前缀、只写新增内容，长期写入量约为 `S + Nq`，主要不随 `M` 改变，其中 `S` 是初始稳定前缀，`N` 是观察期轮数。此时缩短间隔、减小滞后都会减少重复处理，最优解为 **`M=1, K=1`**。默认 5/3 是为不确定上游与近期编辑保留余地，不能称为这种理想机制的成本最优解。

代入示例参数，写入量约为 `6,000 + 1,500N`；若观察 100 轮，则约为 `156,000 tokens`，忽略初始与结束阶段尚未进入缓存的尾部差异。

### 每次推进都重建全前缀时

在同一稳定窗口内、`N` 足够大且忽略首尾周期与滞后的低阶修正时，写入量和尾部量近似为：

\[
W(M)\approx\frac{NS+qN^2/2}{M},\qquad
U(M,K)\approx Nq\left(\frac{M-1}{2}+K-1\right).
\]

若优化目标写成 `C ≈ wW + rU`，其中 `w` 是有效重建成本权重、`r` 是普通输入相对缓存读取的额外成本权重，固定 `K` 后可得：

\[
M^*\approx\sqrt{\frac{w}{r}\left(N+\frac{2S}{q}\right)}.
\]

代入 `S=6,000, q=1,500`，有 `2S/q = 8`，因此：

\[
M^*\approx\sqrt{\frac{w}{r}(N+8)}.
\]

等权重下，不同预期窗口长度对应的连续最优间隔为：

| 预期稳定窗口 `N` | `M* ≈ sqrt(N+8)` | 比较相邻整数后的间隔 |
|---|---:|---:|
| 20 轮 | 5.29 | 5 轮 |
| 40 轮 | 6.93 | 7 轮 |
| 100 轮 | 10.39 | 10 轮 |

以 `N=100` 为例，`W ≈ 8,100,000/M`；默认 `M=5` 对应约 `1,620,000 tokens` 的重复写入量，`K=3` 时额外未缓存历史总量约为 `100 × 6,000 = 600,000 tokens`。这些是忽略首尾周期与滞后修正的近似累计量，不是账单。间隔应限制在观察期内；`N` 是预期稳定窗口的长度，不是简单代入当前累计轮数。

若要预测账单，权重必须与计费语义一致。例如写入、读取、普通输入是互斥计费类别时，总输入费用应写成：

\[
C=p_rT+(p_w-p_r)W+(p_u-p_r)U,
\]

其中 `T` 是总输入 token 量，`p_w,p_r,p_u` 是三类单价。因此对应的权重是 `w=p_w-p_r, r=p_u-p_r`，不能直接把写入标价当作相对读取的增量成本。Gemini 对象创建与后续读取、存储另行计费时，也不能机械套用这一互斥分类公式。

沿用前述价格示例 `p_w=1.25, p_r=0.1, p_u=1`，则 `w/r=1.15/0.9≈1.278`。在 `N=100` 时，`M*≈sqrt(1.278×108)≈11.75`，比较相邻整数后为 12 轮。它与等权重下的 10 轮不同，也说明固定 5 轮不能被视为普适最优解。

`K=1` 的最优结论同样有适用前提：忽略滞后对重写量的影响、没有编辑风险时，减小 `K` 能减少普通尾部；它不是任意价格与编辑概率下的联合最优结论。未来若同时优化 `M` 和 `K`，需保留重建前缀长度的变化并计入编辑导致的失效成本。

### 运行时因素

- Full Agent 一轮可以有多次工具续答；跟进计数按成功提交的正文轮次，计费按实际请求。尾部、工具调用和输出长度并非固定 `q`，需要从请求记录估计。
- Gemini 当前实现按完整前缀指纹创建对象，前缀变化就重建，不向旧对象增量追加；默认 TTL 300 秒，工具定义和工具选择配置也参与内容。截至调查截止日期，缓存对象更新只支持过期时间，计费还包含存储费用。用户停顿与配置变化可能使对象在 5 轮之前就被重建。
- 编辑、重生成、分支、窗口裁剪及常驻资料变化会打破仅追加假设。倒数第 3 的价值需纳入近期编辑概率，不能只看平均尾部长度。
- 缓存读取为零可能来自门槛不足、过期、路由变化或参数被忽略，单次零命中不能证明“全量重写”。缺失的 usage 计数也不能当作零。

后续优化可以复用上述公式，先以固定锚点、前移锚点的受控对照和连续实际 usage 判断复用机制，再结合有效价格、窗口长度、请求频率与编辑风险计算策略。目前没有自动识别增量/重建类型、自动调节间隔或账单最优化；界面允许用户独立配置 `M` 与 `K`。

## 跟进状态与分支一致性

右侧“缓存”页可调整间隔和倒数位置，或切换手动固定；仅本地运行时控制时显示。悬停已完成 AI 正文回复末尾可手动固定整条回复，开场白和工具交换不能作为目标。

策略及进度保存在 `sessions.cache_breakpoint_follow`，包含 `interval`、`offset`、`anchor`、`progress`。修改自动策略或恢复自动会立即定位并归零；之后只在新增正文成功提交的同一事务内推进。重生成、维护、失败和取消不计轮次，重复提交不重复推进。新会话没有目标时先使用固定前缀，即使已有第 3 个回复，也会等到首次跟进间隔再推进。

`PUT /api/sessions/{sid}/cache-breakpoint` 可选传入正整数 `follow_interval`、`reply_offset`，省略时保留已有值；`expected_revision` 防止覆盖并发修改。分支继承策略，自动模式在新分支重新定位、归零；手动位置映射可继承消息 ID，失效选择保留并提示。

目标不在当前分支或实际上下文窗口时，回退到常驻世界书、角色资料或可用固定前缀，不擅自改选另一条正文。缺失跟进策略使用默认 5/3；已经保存的参数不会被新默认覆盖，迁移也保留手动位置。

## 协议适配与 Gemini 生命周期

### 用户可选缓存时效

右侧“缓存”页使用正文模型的 `cache.retention` 配置，按模式独立保存，并使用设置范围修订号防止覆盖并发修改。未设置时值为 `default`，解析为当前协议和模型的最低应用档位。不适用的已保存档位同样解析为最低档，不向服务商发送另一家 API 的值。旧自定义 JSON 中已有的 Claude `ttl`、OpenAI `prompt_cache_retention` 或 `prompt_cache_options.ttl` 会导入此配置；显式选择优先于旧 JSON。

| 路径 | 可选档位与参数 |
|---|---|
| Claude Messages／Chat 兼容 | 5m（默认省略 `ttl`）／1h，内容块 `cache_control.ttl` |
| GPT-5.6 及以后 Chat／Responses | 当前仅 30m，`prompt_cache_options.ttl`；保留本地控制的 `mode` |
| GPT-5.5 Chat／Responses | 当前仅 24h，`prompt_cache_retention` |
| 支持扩展保留的更早 GPT Chat／Responses | in_memory（最低档）／24h，`prompt_cache_retention` |
| Gemini 原生／Google Chat 兼容显式对象 | 应用预设 5m／15m／1h／24h，创建 `cachedContents` 时换算为秒字符串 `ttl` |

以上按 2026-09-30 官方文档实现参数预设，不是中转能力探测。Claude 原生云端模式在用户明确保存时效后发送顶层 `cache_control`，由服务端选择终点，未配置的新云端设置不启用额外控制；Claude Chat 兼容与 Gemini 隐式云端模式不提供时效控制。OpenAI 云端模式仍发送时效而不发送断点。不支持的自定义内容块格式不自动修改 JSON。Claude 1h 可能增加写入单价，Gemini 长时效可能增加存储费用；OpenAI 旧式 24h 表示最长保留政策，不保证始终保留满 24 小时。官方依据：[Claude](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)、[OpenAI](https://developers.openai.com/api/docs/guides/prompt-caching)、[Gemini CachedContent](https://ai.google.dev/api/caching)。

Gemini 对象按连接、凭据、协议、模型和会话保留一个活动槽；前缀、窗口或时效变化时替换并尽力删除旧对象。失效时间取用户选定时长与服务商 `expireTime` 中较早的一项。切换时效不会把旧的长寿命付费对象遗留在另一个配置槽中。

| 接口 | 本地控制方式 |
|---|---|
| Chat Completions | 按模型预设或自定义内容块标记；Google 兼容扩展可引用已创建的 Gemini 对象 |
| Responses | 受支持模型使用 `prompt_cache_breakpoint` 与 `prompt_cache_options`；不假定可引用 Gemini 对象 |
| Anthropic Messages | 原生 `cache_control` 内容块标记 |
| Gemini GenerateContent | 创建 `cachedContents`，生成时引用 `cachedContent`，只发送后缀 |

自动匹配依据模型名称和原生协议，是参数预设而非能力探测结论。未知模型要求自定义参数，否则降级云端。自定义模式允许内容块字段名、JSON 值和请求级 JSON 对象，不能覆盖模型、消息、工具、采样等核心字段。参数错误由服务商返回，不通过删改历史规避。

原生接口仅把固定前缀作为顶层系统指令，动态上下文留在对应的后部位置；工具权限、变量更新、换窗仍由本地校验。原生工具交换保留思考块、签名与调用标识。连接接受根地址和已有 API 前缀，保留部署路径，现有提供商协议不自动切换。

Gemini 对象包含断点之前的系统规则、消息、工具定义与工具选择配置。进程内按凭据指纹、提供商、模型、会话、窗口和前缀内容隔离，默认 TTL 300 秒，可在右侧缓存页改选时长；同一内容和时效且未临近过期时复用，前缀、时效变化或过期时重建。同一连接、凭据、协议、模型和会话仅保留一个活动对象，旧对象尽力删除，删除失败或进程退出后由 TTL 回收。句柄不写入故事快照。

前缀不足本地估算门槛、创建失败或接口不存在时，完整发送上下文并记录降级。服务商必须同时开放对象创建和引用，仅支持生成接口并不足够。Gemini 无法拆分固定系统指令；断点若位于固定系统前缀内部，运行时完整发送并提示改选更后的正文，不擅自扩大缓存范围。

对象失效或服务商明确拒绝缓存字段时，最多重发一次完整请求；超时、断流、普通参数错误与服务端错误不自动重发生成。确定的不支持结果按配置指纹记忆，配置变化、重新检查连接或重启后可再探测。

## 观察、迁移与验证

上下文预览保存计划断点与来源；工作记录保存最终请求、实际 URL、缓存状态、工具定义及前缀摘要。UI 的“已发送”只说明参数发出，不能用 HTTP 200 证明服务商执行了缓存控制。核对时应同时看边界、前缀和工具指纹、读取/写入 usage 与账单。

应用保存原始 usage，缺失计数表示未知。Claude 输入总量包含未缓存输入、读取与创建；Gemini 区分候选输出与思考量；兼容接口识别写入别名。框架内部累计使用独立数值视图，不覆盖应用记录中的未知值。

旧模型设置首次迁移前保存 SQLite 备份；正文配置切换本地控制，保留提供商、模型与手动断点，旧缓存键与保留时长转入附加请求参数。迁移递增对应设置版本，后台配置保持云端模式。

主要验证入口是 `tests/backend/test_cache_follow.py`、`test_session_cache_breakpoint.py`、`test_unified_cache.py` 与 `test_prefix_cache_probe.py`，覆盖计数、分支、四协议最终 HTTP 请求、固定锚点下的前缀复用、Gemini 对象及失败降级。编译顺序另由 Full/Half Agent 上下文测试核对，确保变化的消息与工具提示处于预期位置。

真实服务商对照工具见[Prefix cache diagnostic](../../tools/probe_prefix_cache.md)，仅使用短输出合成样本，日志写入被忽略的 `.cache/`。测试结果只描述被测端点与模型，不能推断中转内部转换或所有服务商表现。

真实项目回合的审计入口见[验证与发行](../development/validation.md)：`tools/audit_runtime_cache.py` 从运行数据库读取请求与原始用量，核对包含工具定义的最终 HTTP 缓存前缀。兼容接口的缓存写入识别 `cache_write_tokens`、`cached_creation_tokens` 和 `cache_creation_tokens` 三种 details 字段；保留真实的 0，不把缺失字段当作 0。同一中转的 Chat Completions 与原生 Messages 路径可能具有不同的缓存和工具转换行为，出现稳定前缀却大量重写时应分别实测，不能仅凭 `status=sent` 判定已命中。

## 历史导航与渲染

对话刻度栏以约 12px 的间隔垂直居中排列，历史增加时向上下展开；达到可用高度后采样显示刻度。按回合提供预览、点击/拖动跳转、方向键及 Home/End 定位；白色表示阅读位置，黄色表示计划断点。引用原文、定位缓存和历史导航共用消息定位入口，覆盖当前分支完整历史；UI 渲染范围不影响模型上下文。

不超过 120 条消息且正文合计不超过 20 万字符时直接渲染，否则升级为动态高度虚拟列表，前后各保留一屏缓冲，同一视图只升级不降级。高度索引按实际消息、世界书与工具记录测量，编辑中的消息保持挂载，Full Agent 工具摘要按需加载并去重。

脚本交互消息首次进入范围才加载，之后保留实例到退出会话视图，避免重复运行或丢失草稿；离屏减少绘制但不暂停脚本，实例内存可能随浏览增长。普通正文 DOM 不随历史浏览累计。后端仍一次返回完整分支历史，未引入服务端分页。

浏览器验收入口是 `python -m tests.browser.browser_history_navigation` 和 `python -m tests.browser.browser_history_rendering`，覆盖两模式、短对话、一万条历史、断点交互、脚本状态与多视口；结果和截图写入 `.cache/history-navigation/`。
